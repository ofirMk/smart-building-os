# Priority — Supplier Screen Reference

> תיעוד הדרגתי של 28 תמונות רפרנס ממסך הספקים ב-Priority ERP.
>
> **מטרה**: איסוף **תוכן** (אילו שדות, sub-entities, tabs, workflows) לא
> **UI style** — זה יישאר BentoSmartList + MasterDetailShell בסטנדרט של
> מרקר אופק. Priority היא מקור דרישות, לא מקור עיצוב.
>
> **שיטה**: לא מתחילים לפתח עד שיש את כל 28 התמונות. אחרי שהכול מתועד,
> מזקקים ל-scaffold אחד.

## פירוט לפי תמונה

### תמונה #1 — Tab עליון "פרטים נוספים" + Tab תחתון "אנשי קשר לספק"
יש popup: *"ייפתח חשבון 200005 שיקושר לספק"* — סימן לכך שיצירת ספק מזניקה
פתיחה אוטומטית של חשבון ראשי במערכת (GL integration). כדאי להזכר
בפיצ'ר אוטומציה — לא חלק מה-UI אלא trigger עסקי.

**שדות "פרטים נוספים":**
- עמודה ימין: `סניף`, `מחסן קבלן משנה`, `מחסן קונסיגנציה`, `תחום עיסוק`, `שנת הקמה`, `מספר עובדים`, `סוג ספק`, `סוג הזמנה`
- עמודה שמאל (checkboxes + flags): `שינוי שם?`, `הדפסות באנגלית?`, `ספק חסוי?`, `דרגת הרשאה`, `נספחים?`, `הצעה במרקטניס`

**עמודות גריד "אנשי קשר לספק":** `שם *`, (שדות לא-קריאים), `שם פרטי`, `שם לועזי`, `לטיפול *`, `טלפון`

### תמונה #2 — אותו מסך, highlight על checkbox "שינוי שם?"
ה-checkbox מסומן בסימון אדום — רמז שזה flag חשוב שצריך UX מיוחד
(אולי דורש אישור / יוצר revision record?). **שאלה פתוחה ללקוח**:
מה קורה כשמסמנים "שינוי שם?" — האם זה מייצר history/audit?

גריד תחתון בתמונה זו הוא "אנשי קשר לספק" עם אותן עמודות — עמודת `לטיפול`
היא per-contact (כל איש קשר לטיפול של משתמש ERP שונה).

### תמונה #3 — Tab עליון "כתובת וטלפון"
- **כתובת** (עמודה ימין): `כתובת` (dropdown — רמז למספר כתובות שמורות),
  `כתובת - שורה 2`, `כתובת - שורה 3`, `עיר`, `מדינה`, `עיר ומדינה` (שדה מחושב?),
  `ארץ`, `מיקוד`
- **טלפון** (עמודה שמאל): `טלפון`, `פקס`, `e-mail`, `Web Site`

**שים לב לתפריט הצד השמאלי** (נראה חלקית): ספקים, משמ…, שורות…, הגדרות ישיר…,
תיעודי ע…, **חשבוניות**, **מחירוני**, **הזמנות** (×2), **Vendor**, מנהל ת…, ניהול ת…
→ זה תפריט cross-entity drill של Priority ("קישורים קשורים לרשומה הפעילה"),
**לא** child tabs. זה מנגנון UX נפרד — בדומה ל-"actions menu" או
"related records". צריך להחליט אם נבנה כזה אצלנו. **החלטה לפי יתר התמונות**.

### תמונה #4 — Child tab "אנשי קשר לספק" עם sub-form פתוח
ברגע שנבחר איש קשר בודד (בתמונה: "סיון שבל", סטטוס פעיל, לטיפול "מאיה"),
נפתח sub-form עם 3 sub-tabs:

1. **טלפונים** (active): `טלפון ראשי`, `טלפון נייד`, `טלפון במשרד`,
   `טלפון בבית`, `פקס`, `e-mail`
2. **תפקיד וצוות**
3. **דגלים**

**משמעות UX:** גם "אנשי קשר" הוא master/detail פנימי (איש קשר = master,
פרטי הטלפון/תפקיד/דגלים = detail). זה בעצם **master/detail דו-רמתי** —
ספק מכיל אנשי קשר, ואיש קשר מכיל פרטי קשר. **חייב לחשוב איך זה מיוצג
במודל שלנו.**

עוד מידע בגריד: `שם פרטי`, `שם משפחה`, `שם` (מחושב? או full name?),
`שם לועזי`, `סטטוס *`, `לטיפול *`.

### תמונה #5 — Child tab "מוצרים לספק"
עמודות הגריד: `מק״ט *`, `תאור מוצר *` (בתמונה "די ספקד. דרגדרנדת ד"
— placeholder), `מק״ט ספק/יצן`, `תאור מק״ט ספק/יצן`, `הצעת מחיר`,
`שם יצן`, `שם מלא יצן`, `משפחה`, `תאור משפחה`, `זמן אספקה בעיד`

**פרשנות:**
- `מק״ט` = ה-SKU של **החברה שלנו** (שמופיע בקטלוג הפריטים).
- `מק״ט ספק/יצן` = ה-SKU של הספק/יצרן (Supplier SKU / Manufacturer SKU).
- `הצעת מחיר` = מחיר נוכחי מהספק (quote).
- `משפחה` / `תאור משפחה` = Item family/category.
- `זמן אספקה בעיד` = Lead time בימים.

**קשר לפיצ׳רים שלנו:** ה-tab הזה הוא המקבילה של
`/api/master-data/items/[id]/suppliers` שכבר יש לנו (Phase 7.14.3), רק
הפוך — מנקודת מבט הספק. התוכן זהה: מיפוי Item ↔ Supplier עם מחיר ולידאוט.
טוב, זה אומר שאנחנו **כבר** יכולים לספק את ה-tab הזה מאחורי הקלעים, רק
צריך צד לקוח חדש.

# Batch #2 — תמונות 6–10 + הקלטה מהנרטיב

> הלקוח צירף narrator transcript בארבעה בלוקים עסקיים. הוא קריטי —
> הוא הופך את התמונות מ-UI-photos לכללי-עסק. משולב להלן.

## כלל-עסק #1 — יצירת ספק + AUTO GL ACCOUNT

**Flow**: `רכש → ספקים` → מילוי `שם ספק` → המערכת מקצה `מס.ספק`
**אוטומטית** לפי תבניות → ברגע יציאה מהרשומה (commit), **נפתח חשבון
הנה"ש אוטומטית** שמקושר לספק. מאושש בתמונה #10 (popup Priority 17:
*"ייפתח חשבון 200005 שיקושר לספק"* עם אישור/ביטול).

**השלכה אצלנו**:
- צריך **numbering scheme** מוגדר מראש (`erp_md_suppliers.supplier_number`
  הוא manual כרגע — לבדוק אם יש auto-number trigger).
- אחרי יצירת ספק חובה להפעיל **GL bootstrap** — יצירת חשבון GL מקושר.
  בדיקה: האם `erp_md_suppliers` מחובר כבר ל-`erp_gl_accounts` via FK /
  trigger? אם לא — זה פיצ׳ר מובהק.
- ה-popup הוא audit/confirmation — הסוכן ידע בדיוק מה עומד להיפתח.
  אצלנו זה יכול להיות inline confirmation ב-EntitySaveBar.

## כלל-עסק #2 — "שינוי שם?" + "ספק מזדמן" + "הדפסות באנגלית"

שלושת ה-checkboxes שמופיעים ב-Tab "פרטים נוספים" אינם קוסמטיים:

| Flag | משמעות עסקית |
|---|---|
| `שינוי שם?` | **מאפשר** עריכה של שם הספק בתעודות שכבר הופקו. ללא הסימון — השם נעול בתעודות ישנות. צד אצלנו: history table ל-`erp_md_suppliers.name`? |
| `ספק מזדמן` | Flag שמשנה את ה-onboarding flow (פחות שדות חובה — למשל אין drill ל"הגדרות כספים"). מתאים לקבלן עבודה חד-פעמי. |
| `הדפסות באנגלית?` | כשמסומן, PDF-ים ותעודות שמופקים לספק יהיו באנגלית עם **טקסט קבוע** שהוגדר לכך. אצלנו: הטריגר קיים (`body_html_english` ב-`erp_purchase_orders`), אבל אין per-supplier toggle. זה **פיצ׳ר חסר** במערכת שלנו. |

## כלל-עסק #3 — "איש קשר להצעה" = DEFAULT CONTACT

בגריד "אנשי קשר לספק" יש flag `איש קשר להצעה`. כשמסומן, **בכל בקשה
להצעת מחיר (RFQ) שתישלח לספק, איש הקשר הזה הוא ברירת המחדל**.

**השלכה**: זה enforcement rule, לא תצוגה. אצלנו: `erp_supplier_contacts.is_rfq_default`?
לבדוק. גם שימושי ל-"שלח הזמנה" (`/api/procurement/orders/[id]/send`)
— לבחור אוטומטית את ה-email של איש הקשר הזה.

## כלל-עסק #4 — "מוצרים לספק" = ENFORCEMENT, לא רק מידע

הנרטיב אומר: *"לאחר רישום פריטים במסך מוצרים לספק, **רק הם** יופיעו
ברשימות הבחירה של התעודות המשויכות לאותו ספק"*.

זה **כלל עסקי חזק**: כשיוצרים PO לספק X, ה-dropdown של פריטים
מסונן רק לפריטים שמופיעים ב-`supplier_products(supplier_id=X)`.
אם הרשימה ריקה — אין פריטים לבחור.

**אצלנו**: לבדוק אם `/api/procurement/orders/new` מסנן את ה-items לפי
הספק שנבחר. ייתכן שלא — זה פיצ׳ר **מיד-to-make** אחרי שנבין את
המצב הקיים.

## כלל-עסק #5 — "מסמכים לספק"

Sub-tab חדש שנחשף בתמונה #6. גריד עם העמודות:
`שם קובץ *`, `תאריך יצירת הקובץ`, `נתיב הקובץ *`, `סטטוס *`, `סיומת`,
`לא לש?` (לא לשתף?), `גודל קובץ בבתים`, `עדכן ע״י`, `ת. עדכון אחרון`,
`נועל ע״י` (file lock — checkout/checkin?).

**אצלנו**: אולי להרחיב את `erp_digital_assets` להכיל גם `supplier_id`
(היום זה מקושר לפריט). או טבלה חדשה `erp_supplier_documents`.

## מסך נפרד — "הגדרות כספים לספקים" (תמונה #9)

**Flow כניסה**: מעמודת "מספר ספק" במסך הספקים → **הפעלה ישירה**
(Priority convention → אצלנו: drill-in מכפתור/context menu).

> **החלטת UX חשובה**: Priority מפצלת את זה למסך נפרד כי זה אריח
> פיננסי-מוכוון-הנה״ש. אצלנו יש שתי אופציות:
>   (א) **Tab נוסף** ב-supplier 360 ("כספים") — אחיד לסטנדרט שלנו.
>   (ב) **מסך נפרד** עם שלו MasterDetailShell — יותר ברור לאנשי כספים.
>
> המלצה: (א) — tab. לא להמציא מסך חדש בלי סיבה; "כספים" כבר בסטנדרט
> של ה-supplier-360 tabs במרקר אופק ב-Priority.

### Header של "הגדרות כספים לספקים"

`ספק *` (PK), `שם ספק`, `מטבע *`, `מס. עוסק מורשה`, `מספר תיק במע"מ`,
`חשבון בהנה"ש`, `סטטוס`.

### Tabs עליונים (4 tabs)

1. **פרטים כלליים** (active ב-#9) — חשבונות GL, ברירות מחדל:
   - `סוג תנועה - חש. ספק` (default journal entry type for invoices)
   - `סוג תנועה - זיכוי מהספק` (default journal entry type for credit notes)
   - `עיגול מחיר בחשבונית?` (boolean)
   - `תשלום בהעברה בנקאית?` (boolean) — **קובע אם תהליך הכנת
     תשלומים יבצע wire transfer או checks**
   - `חשבון לזיכוי` (GL account)
   - `חשבון קניות` — **default GL account שנרשם אוטומטית בחשבוניות
     מאותו ספק**
   - `מרכז רוח/עלות` (cost center default)

2. **ניכוי מס במקור** — Withholding tax:
   - `אחוז הניכוי המאושר`
   - `תאריך תוקף`
   - `קוד פקיד שומה`
   - `מספר תיק במס הכנסה`
   - `תוקף אישור ניהול ספרים` — **kill-switch**: אחרי תאריך זה
     המערכת **חוסמת רישום תשלום לספק**. זה regulation critical.

3. **חשבונית ספק** — default נוספים לחשבוניות ספציפיים מאותו ספק.

4. **חתימה** — חתימה דיגיטלית? לא ראיתי עדיין תוכן.

### Sub-grids (tabs תחתונים ב-"הגדרות כספים")

כולם 1:N על הספק הפיננסי:

1. **פרטי חשבון בנק** — עמודות: `מס. חשבון בנק *`, `קוד הבנק *`,
   `שם הבנק`, `סניף בנק *`, `IBAN`, `ניכוי מס מדורג`, `לוג שינויים`,
   `מיסים נוספים`, `כתובת`, `כתובת - שורה 2/3`, `עיר`.
   **מתמלא אוטומטית בעת העברה בנקאית**. ניתן לשנות נקודתית →
   השינויים נשמרים ב-**sub-grid "לוג שינויים"** (3-level nesting!).
2. **כתובת למשלוח המחאות** — אם שונה מכתובת הספק הראשית.
   שדות: `שם *`, `איש קשר`, `טלפון`, `פקס`, `שלמו לפקודת`,
   `כתובת`, `כתובת - שורה 2/3`, `עיר`, `מדינה`, `מיקוד`, `ארץ`.
3. **עלויות יבוא למוצרי ספק** — לצורך landed-cost על imports.
4. **עמלות FOB למשפחות מוצר** — עמלות FOB per item-family.
5. **ניכוי מס מדורג** — אם ה-withholding תלוי ב-tier (לא flat %).
6. **לוג שינויים** — audit trail למסך.
7. **מיסים נוספים** — VAT sub-rates, excises, other.

### רשימת מטבעות נתמכים (מ-dropdown תמונה #9)

ש"ח | $ (דולר) | EUR (יורו) | GBP (ליש"ט) | JPY (ין יפני) |
AUD (דולר אוסטרלי) | CAD (דולר קנדי) | JOD (דינר ירדני) |
DKK (כתר דני) | NOK (כתר נורבגי) | SEK (כתר שוודי) |
LBP (לירה לבנונית) | EGP (לירה מצרית)

→ אצלנו `erp_purchase_orders.currency` כבר קיים. `erp_md_suppliers`
צריך `default_currency`. לבדוק.

### אוטופיל מרשויות המס (שע"מ / 1000)

**פיצ'ר קריטי**: במקום להזין כל שדה מס ידני, המשתמש יכול לרשום רק
`מס. עוסק מורשה` או `מספר תיק מס הכנסה` → המערכת מושכת את יתר
הנתונים מרשויות המס (שירות ע״מ / טופס 1000) אוטומטית.

**אצלנו**: יש `@/lib/pikoud` (אמורים להיות חיבורים), אבל לא בטוח
שיש integration עם שע"מ. פיצ'ר שצריך בדיקה נפרדת — **לא חייב ב-v1**
של המסך.

## תגלית #1 — Sub-sub-child: "הוצא על ניכוי מס" (תמונה #16)

ב-breadcrumb הצדדי רואים היררכיה:

```
ספקים (supplier master)
 └─ הגדרות כספים לספקים (financial config card)
     └─ ניכוי מס במקור (tab)
         └─ הוצא על ניכוי מס (sub-grid) ← "שורה 1/1"
```

זהו **3-level drill** — כל שורה ב-"הוצא על ניכוי מס" היא **רשומת

**השלכה אצלנו**: טבלה מנורמלת `erp_supplier_withholding_approvals`
(לא שדה בודד על הספק) — כל אישור עם תוקף start/end וקובץ מצורף (אם יש).
ה-"פעיל כרגע" הוא ה-record עם `valid_from <= today <= valid_until`.
זה גם מאפשר לראות היסטוריה: "מה היה הניכוי ב-2022?"

## תגלית #3 — Integration שע"מ / 1000 (תמונה #17 — FAQ)

תמונה #17 היא **Help page** של Priority שמסבירה את ה-flow:
*"יעד לטעון נתוני ניכוי מס במקור של ספקים באמצעות מערכת 1000 של מס הכנסה"*.

### התמצית

- **רשות המס (משא"ם / 1000)** מחזיקה את כל אישורי ניכוי המס הקיימים
  בישראל. ספקים מחדשים את האישור שלהם מול רשות המס, לא מולכם.
- Priority מאפשרת **bulk-file sync**: צור קובץ (`sys1000.txt`) שמכיל
  את כל מספרי העוסק/תיק של הספקים שלך → עלה לפורטל `misim.gov.il` →
  קבל קובץ חזרה עם האחוזים והתוקפים המעודכנים → טען ל-Priority.
- Priority גם מזהה ספקים **ללא תיק מ"ה או עוסק מורשה** (כ-errors)
  ומציע מסך לתיקון.
- File naming convention: `Takin_n_של_החברה_YYYYMMDD.n`.

### המשמעות אצלנו

- **ב-v1 של מסך הספקים**: לא נדרש. המשתמש ימלא ידנית כמו ב-Priority
  לפני שהם הטמיעו את הbulk flow.
- **v2 אופציונלי**: אפשר לבנות endpoint `POST /api/suppliers/tax-sync/export`
  שמייצא את הקובץ ו-`POST /api/suppliers/tax-sync/import` שקולט
  את התשובה. זה **פיצ׳ר integration**, לא UX — אפשר לפתח בנפרד.
- **הערת סיכון**: פורמט הקובץ הוא של רשות המס; אם הוא משתנה, ההתממשקות

(לא מוצרים בתוך מחירון — אלה ב-drill-in הבא):

| קוד מחירון ספק | תאור | ת. כניסה לתוקף | בוטלה? | מטבע | מנפל מחיר | שם יצרן |
|---|---|---|---|---|---|---|
| 2001 | (linked) | 01/01/13 | false | ש"ח | (empty) | (empty) |

### עמודות מלאות

`קוד מחירון ספק *`, `תאור מחירון ספק`, `ת. כניסה לתוקף *`,
`כניסה לתוקף מבוטלת` (bool), `מטבע *`, `ישראל קוד מ`,
`מנפל מחיר`, `שם יצרן`, `שם מלא יצרן`.

### תובנה: מודל "מחירון = ראש + שורות"

המבנה הוא **header/lines**:

```text
erp_supplier_price_lists (header)
  ├─ id
  ├─ supplier_id
  ├─ code (e.g. "2001")
  ├─ description
  ├─ effective_from (date)
  ├─ cancelled (bool)
  ├─ currency
  └─ manufacturer_name (nullable)

erp_supplier_price_list_items (lines)
  ├─ id
  ├─ price_list_id
  ├─ item_id (mapped to supplier SKU)
  ├─ unit_qty
  ├─ unit_price
  ├─ discount_pct
  ├─ price_after_discount
  └─ customer_price (price for end customer)
```

**Status אצלנו**: יש לנו `erp_supplier_pricing` (price per item per
supplier — flat). זה **שונה** מהמודל של Priority (price-list grouping).
שיפור עתידי: לאמץ price-list grouping. כרגע MVP — להציג את ה-pricing
הקיים שלנו ב-tab זה.

## תגלית #2 — מסך "מחירוני ספקים" + audit log (תמונה #27 — קריטית!)

זה ה-**drill-in** מתוך ה-tab של תמונה #26: לחיצה כפולה על שורת
מחירון פותחת מסך **נפרד** עם **3-level layout**:

### Level 1 — Header (Master, top)

`קוד מחירון ספק = 2001`, `שם ספק = רהיטים ללל בע"מ`, `מס. ספק = 2001`,
`ת. כניסה לתוקף = 01/01/13`, `מטבע = ש"ח`. (12 שדות בסה"כ).

### Level 2 — מחירי מוצרים (Detail grid, middle)

| מק"ט ספק | תאור | כמות | יח' | מחיר ליחידה | הנחה (%) | מחיר אחרי הנחה | מחיר ללקוח |
|---|---|---|---|---|---|---|---|
| 001 | כסא "כרמית" | 1 | יח' | 35.0000 | 0.00 | 35.0000 | 0.0000 |
| 002 | כסא "רוית" | 1 | יח' | 40.0000 | 0.00 | 40.0000 | 0.0000 |
| 003 | כסא "דוד" | 1 | יח' | 45.0000 | 0.00 | 45.0000 | 0.0000 |
| 011 | שולחן משרדי 120X60 | 1 | יח' | 80.0000 | 0.00 | 80.0000 | 0.0000 |
| 012 | שולחן משרדי 180X60 | 1 | יח' | 88.0000 | 0.00 | 88.0000 | 0.0000 |
| 013 | שולחן 200X120 | 1 | יח' | 99.0000 | 0.00 | 99.0000 | 0.0000 |

יש tab משני (פתוח כאן): **"מחירי מוצרים"** + tab נוסף: **"חתימה
אלקטרונית"** (אישור דיגיטלי של המחירון).

**הערות בולטות**:
- 4 ספרות אחרי הנקודה ב-`מחיר ליחידה` — דיוק גבוה לחישובי עלות.
- "מחיר ללקוח" עומד על `0.0000` בכל השורות — שדה מוטמע אך לא בשימוש
  בדוגמה. מרמז על feature `markup pricing` (מה הלקוח שלי משלם).

### Level 3 — לוג שינויים (Audit log, bottom — תגלית חדשה!)

זה **3-level nesting** מסוג `audit log per price line`:

| שדה | ערך ישן | ערך חדש | חתימה | שם איש קשר | תאריך | פרטים |
|---|---|---|---|---|---|---|

(הריק — כי הדגמה לא הראתה שינויים, אבל המבנה מוצהר)

**זהו דפוס "לוג שינויים אוניברסלי"** שיופיע גם ב-tabs אחרים (חשבונות
בנק, ניכוי מס במקור). הוא מאחסן change events לכל שדה מהותי.

### אצלנו — המלצה ארכיטקטונית

טבלה גנרית `erp_audit_log`:

```sql
CREATE TABLE erp_audit_log (
  id uuid PRIMARY KEY,
  company_id uuid NOT NULL,
  entity_type text NOT NULL,  -- 'supplier_price_line' | 'bank_account' | ...
  entity_id uuid NOT NULL,
  field_name text NOT NULL,
  old_value text,
  new_value text,
  changed_by uuid REFERENCES auth.users(id),
  contact_name text,
  changed_at timestamptz DEFAULT now(),
  details jsonb
);
CREATE INDEX ON erp_audit_log (entity_type, entity_id, changed_at DESC);
```

DB triggers על שדות sensitive → INSERT אל `erp_audit_log` אוטומטית.

### סיכום nesting depth

עומק ה-drill-in המקסימלי שראינו:

```text
1. Suppliers list (master)
   ↓ click row
2. Supplier card (entity)
   ↓ click "מחירוני ספק" tab
3. Price lists list (detail tab data)
   ↓ double-click row → opens dedicated screen
4. Price list detail (header + lines + audit)
   ├─ Header (1 record)
   ├─ Lines: מחירי מוצרים (N items)
   └─ Audit log: לוג שינויים (per-line changes)
```

**4 levels טבעיים** עם audit כ-meta-layer. ה-MasterDetailShell שלנו
תומך ב-2 levels טבעיים (Master + Detail-tabs). עבור levels 3+ אנחנו
**נתאם דרך ניווט מלא** (דף נפרד) — זה גם UX יותר נכון.
