|---|---|---|

| **הפעלות ישירות** | מסכים, תכניות ודו"חות שניתנים להפעלה ישירה ממסך מסוים ללא מעבר בתפריטים. | action dropdown / inline operations |

| **הודעת אזהרה** | "קופצת" אבל מאפשרת להמשיך. | warning toast |
| **דוח** | שליפת נתונים בפורמט HTML. עמודה יכולה להיות קלט. | report page with filters |

## 2. כלי ניהול מרכזיים ב-Priority

- **BPM (ניהול תהליכים עסקיים)** — הגדרת תהליך עבודה לגבי כל תעודה: באלו סטטוסים מותר לשהות, לאילו מותר לעבור. שליחת הודעות אוטומטיות למשתמש/קבוצה/מייל.
- **מחולל חוקים עסקיים** — הגדרת חוקים המופעלים כתוצאה משינוי ברשומות/שדות. שליחת הודעות, הצגת אזהרות, הטלת הגבלות.
- **מחולל נתונים** — רישום ערך בעמודה מסוימת כאשר מתקיימים תנאים.

> זה בדיוק מה שאנחנו בונים כ-**Form Engine + Triggers + AI Copilot**.

## 3. מודל הרשאות פריוריטי

> "ניהול ההרשאות ב-Priority מתבצע באמצעות **סיור ההרשאות**. ההרשאות ניתנות לפי קבוצות כך שכל המשתמשים באותה קבוצה יחלקו את אותן ההרשאות."

> "לכל ישות במערכת (תפריטים, מסכים, עמודות במסך, תכניות ודוחות) ניתן להגדיר הרשאות שונות לכל חברה / ראש קבוצה (**חסימת גישה, קריאה בלבד, הסתרת תוכן עמודה וגישה מלאה**)."

> "כמו כן ניתן להפוך הודעת אזהרה להודעת שגיאה." *(= escalate warning to error by user group)*

**מקבילה אצלנו**: RLS + per-column visibility (to be formalized in `permissions-matrix.md`).

## 4. תהליך רכש (מודולים מרכזיים שמשפיעים על כרטיס פריט)

### 4.1 תשתיות רכש
לפי הסעיף: "באתחול המערכת יוקמו נתוני התשתית הבאים":
1. **פריטים (מק"טים)**
2. **ספקים**
3. **מק"ט ספק** (mapping)
4. **מחירוני ספקים**
5. **הזמנות מסגרת**

> "בשוטף, כאשר עולה צורך בפריט שלא קיים יש לפנות לאיש הרכש (איש הרכש יקים פריט חדש או יפנה את העובד לפריט המתאים לצרכיו בקטלוג)."

### 4.2 הזמנת רכש — תהליך
1. **טיוטה** → "הזמנת הרכש תפתח ע"י מחלקת הרכש בסטטוס טיוטה."
2. **פרטים** → "במסך פירוטי הזמנת רכש יפורטו אוטומטית הפריטים לפי הדרישה המקושרת."
3. **אישור** → "לאחר סיום ההקלדה ההזמנה תועבר לסטטוס מאושרת (לא נדרש חתימה של גורם נוסף למקליד ההזמנה)."
4. **שליחה** → "לאחר אישור, ההזמנה תשלח לספק... ניתן להגדיר לכל ספק מייל/פקס/דוא"ל... לתעד את השליחה בפועל — להעביר את סטאטוס ההזמנה ל'נשלחה' באופן ידני."
5. **סגירה אוטומטית** → "הזמנה מאושרת/נשלחה תעבור אוטומטית לסטטוס סגורה עם סיום קבלת הפריטים המוזמנים."
6. **כללי עדכון** → "לא ניתן לשנות הזמנת רכש מאושרת. כדי לשנותה צריך להעביר לסטטוס 'טיוטה' ולבצע את השינויים."

### 4.3 קבלת סחורה
- מתבסס על הזמנת רכש אחת או יותר.
- שורות מגיעות אוטומטית מההזמנה; המשתמש מעדכן את הכמויות שהתקבלו.
- **טיוטה → סופית**: "רק תעודות סופיות יכולות להיות מקושרות לחשבונית."
- **ביטול**: "תעודות קבלה סופיות שלא קושרו לחשבונית ניתן יהיה לשנות באמצעות הרצת התכנית **ביטול סגירת תעודה**."

### 4.4 חשבונית ספק מרכזת
- מקושרת לתעודות קבלה סופיות.
- הנהלת חשבונות מקלידה; חשבונית נסרקת ומצורפת כנספח.
- חשבונית זיכוי + חשבונית לחיוב ספק — מנוהלות בנפרד.

**השלכה על כרטיס פריט**: הוא הבסיס לכל השאר. אם לא מקימים אותו נכון — הרכש לא יעבוד.

## 5. מודול פרויקטים + בקרה תקציבית (ייחודי לבנייה)

### 5.1 היררכיה תקציבית
מתוך המסמך, סעיף 5.2:
```
פרק
 └─ תת-פרק
     └─ נושא
         └─ משאב
```

> "הגדרת תת פרק ומשאב ברירת מחדל **למשפחות מוצר**" (סעיף 5.2.5)
> "הגדרת תת פרק ומשאב ברירת מחדל **למק"טים**" (סעיף 5.2.6)

**זה בדיוק מה שיש לנו**:
- `erp_md_product_families.default_budget_sub_chapter` + `default_resource_id`
- `erp_md_items.budget_sub_chapter` + `resource_id` + `*_manual_override` flags

### 5.2 תקופות בקרה
- **מהדורת תכנון** → תקופת בקרה (חודשית).
- **ביצוע איסוף נתונים לתקופה**.
- **ניתוח עלויות שנאספו**.
- **משטח עבודה לעדכון תת-פרק ומשאב**.
- **עדכון צפי לגמר (הכנסות/הוצאות)**.
- **תכנון מול ביצוע**.
- **התראה על חריגה** מתקציב בתעודות.

**השלכה**: כשתגיע העת לבנות מודול בקרה תקציבית, זה המפרט.

## 6. מודול מכרזים (סעיף 7)

תהליך סטנדרטי:
1. **הקמת כותרת המכרז** + פרטים כלליים.
2. **ניהול מהדורות מכרז**.
3. **הכנסת כתב כמויות** (BOQ).
4. **הכנסת מחירים** — ידנית או אוטומטית.
5. **סעיפים שרוצים לקבל הצעת מחיר מקבלנים**.
6. **פתיחת הצעות מחיר לקבלנים באופן אוטומטי על פי כתב כמויות**.
7. **שליחת הצעה לקבלן/ספק וקליטת מחירים**.
8. **השוואת הצעות מחיר מקבלנים**.
9. **עדכון הצעה זוכה** (דגל "הצעה זוכה" במסך 'הצעות מחיר מספקים', דגל "סעיף זוכה" במסך 'הצעות מחיר - פרוט').

מצב אצלנו: יש מודול מכרזים עם תשתיות רלוונטיות (`erp_vendor_quotes`, `erp_vendor_quote_lines`). כיסוי מלא של תהליך זה — לא חוסם את כרטיס פריט.

## 7. מודול כספים (סעיף 8)

> "הנהלת החשבונות במערכת Priority הנה מלאה ומקיפה. מערכת הכספים ב-Priority מקושרת עם שאר המודולים (מכירות, רכש וניהול מלאי) באופן כזה שפעולות רלוונטיות המתבצעות במערכת כלשהי באות לידי ביטוי ישיר ומידי במערכת הכספים."

**תת-מודולים שהוזכרו**:
- כספים - מכירות (חשבוניות לקוחות, משלוחים)
- כספים - רכש (חשבוניות ספק, השוואה לקבלת סחורה, תשלומים)
- תמחיר וערך המלאי (ממוצע נע / FIFO / תקן)
- ניהול תקציב (התחייבויות → דרישה → הזמנה → קבלה)
- מרכזי רווח ועלות עקיפה
- ניהול קופה

**השלכה**: שכבת הכספים אצלנו תשאב לוגיקה מכאן בפיתוח המודולים של centralized/partials/AR-AP.

## 9. עקרונות שמשפיעים על הארכיטקטורה שלנו

מהמסמך:
1. **כל ספק — סוג הסכם מוגדר**: מחירון ספק / הזמנת מסגרת / הצעת מחיר.
2. **ברירת מחדל חכמה**: "אם לא יבוסס על הצעה או הזמנת מסגרת, המחיר לשורת הרכש יגיע לפי מחירון ספק אם קיים."
3. **מסכי בן לתקשורת**: "במסך הזמנת רכש - טקסט ניתן לרשום הערות להזמנה."
4. **בקרה דו-כיוונית**: מקבלות סחורה → עדכון יתרת הזמנה; מחשבוניות → אישור קבלת סחורה.
5. **פרויקטים כלליים**: "יוקמו פרויקטים כלליים עבור רכש שאינו ישיר לפרויקט ביצוע. למשל, הנהלה וכלליות, עקיפות."

## 10. מה חשוב לזכור לגבי Onboarding לל"טמן הספציפי

- תיאום תכנון וביצוע **מערכות יועץ חשמל** בבנייה למגורים ומסחר
- במערכת **תוקם סביבת עבודה אחת** (single company, במונחים שלנו `company_id`)
- **מנהל הפרויקט** מתקשר למשרד ומבצע הזמנת רכש **טלפונית** → הקלדה במשרד
- **קבלות סחורה חתומות** מגיעות למשרד מהאתרים **פעם בשבוע** (BPM implication — lag tolerant)
- **חשבוניות ספק** נקלטות במשרד ע"י **הנהלת חשבונות** (role boundary)
- **פרויקטים כלליים** לרכש לא-ישיר — הנהלה וכלליות, עקיפות (צריך טופס פרויקט גנרי)
